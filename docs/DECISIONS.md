# Архитектурные решения (ADR)

Формат: `ADR-NNN | статус | дата`. Статусы: `accepted`, `proposed`, `rejected`,
`superseded`.

---

## ADR-001. Стратегия отвечает только за сигналы

**Статус:** proposed (целевое состояние, см. `STRATEGY_CONTRACT.md` §4)
**Дата:** 2026-10-22

**Контекст.** Сейчас каждая стратегия содержит копию цикла симуляции (~130 строк),
`check_last_signal` и `execute_live_trades`. Логика выхода (TP/SL) и расчёт денег
дублируются, бэктест и live расходятся, новая стратегия требует ~500 строк копипасты.

**Решение.** Стратегия реализует `detect_signals()` (чистая функция) и, при
необходимости, `ExitPolicy`. Симуляция, размер позиции, комиссии, метрики, live-исполнение
— в общих компонентах (`TradeSimulator`, `BaseStrategy`, `TradingOrchestrator`).

**Альтернативы.**
- Оставить как есть: быстро, но каждая новая стратегия умножает дублирование. Отклонено.
- Сделать «полный фреймворк» (события, плагины, DI-контейнер): избыточно для одного
  разработчика. Отклонено.

**Следствия.** Нужна миграция существующих стратегий (T3-10) и тест-паритет (T3-8).
Плюс: одна точка изменения TP/SL и комиссий для всех стратегий.

## ADR-002. `Signal` и `Trade` — единственный формат обмена

**Статус:** accepted (уже реализовано)
**Дата:** 2026-10-22

**Контекст.** Дашборд, аналитика и scheduler должны получать результат одинаково.

**Решение.** `Signal` (`timestamp`, `candle_index`, `signal_type`, `price`, `metadata`)
и `Trade` (полный набор полей, см. `STRATEGY_CONTRACT.md` §2) — контракт между
стратегией и потребителями. Направление кодируется строками `BULLISH`/`BEARISH`
(LONG/SHORT — производные).

**Следствия.** `LiveTrade` остаётся отдельной моделью (другие поля: `lots`,
`position_id`, `status`), но должен иметь явный маппер из `Trade` (T3-7).
`src/backtest/backtester.py` со своим `Trade` — legacy, выводится из эксплуатации.

## ADR-003. PostgreSQL как единое хранилище

**Статус:** proposed
**Дата:** 2026-10-22

**Контекст.** Сейчас два хранилища с одинаковой схемой: SQLite (`repository.py`) и
PostgreSQL (`pg_repository.py`). Часть кода использует одно, часть — другое. Схема
меняется ручными скриптами.

**Решение.** PostgreSQL — единственное хранилище для `market_data`, `live_trades`,
`stop_orders`. Миграции — Alembic. SQLite допускается только для тестов и локального
прототипирования (через тот же интерфейс репозитория).

**Следствия.** Нужен интерфейс `TradeRepository` (Protocol) и две реализации;
scheduler переключается на PostgreSQL; данные из `data/live_trades.db` переносятся
одноразовым скриптом.

## ADR-004. Конфигурация через pydantic-settings

**Статус:** proposed
**Дата:** 2026-10-22

**Контекст.** `os.getenv` вызывается в 15+ файлах; отсутствие переменной обнаруживается
в момент первого обращения, иногда в середине торгового цикла. Пароль БД собирается
в URL в 6 местах.

**Решение.** Один модуль `config/settings.py` с `BaseSettings`: типизированные поля,
валидация при старте, `.env` — единственный источник секретов. Доступ через
`get_settings()` (кэшированный синглтон).

**Следствия.** Все модули получают настройки через параметр конструктора (DI), а не
читают env напрямую. Тесты подменяют `Settings` без monkeypatch.

## ADR-005. Время: UTC в хранилище, MSK на выводе

**Статус:** proposed
**Дата:** 2026-10-22

**Контекст.** API отдаёт UTC, `HistoryManager` конвертирует в MSK перед записью,
сделки пишутся `datetime.now()` (naive). Сравнение времён в отчётах и сверках
ненадёжно.

**Решение.** Хранить и сравнивать только timezone-aware UTC. MSK — только для
отображения (дашборд, логи, уведомления). Запрещены `datetime.now()` и `datetime.utcnow()`
— только `datetime.now(timezone.utc)`.

**Следствия.** Нужна миграция данных `market_data.open_time` (сейчас MSK) и
`live_trades.*` (naive) — отдельная задача T1-5. Планировщик продолжает работать в
`Europe/Moscow` (это расписание биржи, не данные).

## ADR-006. Режим торговли задаётся окружением, а не кодом

**Статус:** proposed
**Дата:** 2026-10-22

**Контекст.** `scheduler.py` содержит `DRY_RUN = False`, `TEST_MODE`, тестовые тикеры.
Случайный запуск открывает реальные позиции.

**Решение.** `TRADING_MODE` ∈ {`dry_run`, `paper`, `live`} в env, по умолчанию
`dry_run`. Тестовые сигналы — отдельный флаг `TEST_MODE` в env, не в коде. В `live`
требуется явное `LIVE_CONFIRM=yes` при старте.

**Следствия.** Убирает класс ошибок «забыл переключить флаг». Нужно обновить runbook.

**Реализовано:** 2026-10-22 — `config/trading_mode.py`, дефолт `dry_run`; `live` требует
`LIVE_CONFIRM=yes`, иначе процесс падает на старте. Обнаружено, что прежний `DRY_RUN`
в `scheduler.py` только логировался и не блокировал сделки, а `scheduler_notifier.py`
имел `LIVE_TRADING = True` — оба флага заменены.

## ADR-007. Документация — часть Definition of Done

**Статус:** accepted
**Дата:** 2026-10-22

**Контекст.** Документации не было; знания хранились в коде и памяти автора. Модели,
читающие проект, не могли восстановить контракты.

**Решение.** Любое изменение кода сопровождается обновлением в том же коммите:
`README.md` (если меняется запуск/env), `docs/ARCHITECTURE.md` (структура/потоки),
`docs/CHANGELOG.md` (запись), `docs/DECISIONS.md` (если принято новое решение).

**Следствия.** Документация отражает факт, а не намерения; устаревшие документы
помечаются, а не удаляются молча.

## ADR-008. Удаление legacy-стратегий из реестра

**Статус:** accepted
**Дата:** 2026-10-22

**Контекст.** `strategy_registry.py` импортирует 9 пакетов, которых нет в рабочей копии.
Проект не импортируется. Автор подтвердил: остальные стратегии были примерами схемы
входа/выхода и будут написаны заново.

**Решение.** В реестре остаются только существующие пакеты. Отсутствующие стратегии
не восстанавливаются; их паттерны фиксируются в `STRATEGY_CONTRACT.md` как эталон
контракта.

**Следствия.** `scheduler.py` использует одну стратегию до появления новых; после
T3-3 новые стратегии подключаются одной строкой.

**Реализовано:** 2026-10-22 — реестр сокращён до `sma_crossover` и
`dual_ma_crossover_after_testing`; `import src.strategies.strategy_registry` проходит.

## ADR-009. Зависимости: uv + lock, SDK — вендорным wheel

**Статус:** accepted
**Дата:** 2026-10-22

**Контекст.** Версии зависимостей нигде не фиксировались; `requirements.txt`/`pyproject.toml`
отсутствовали. Официальный индекс SDK `opensource.tbank.ru` временно недоступен, SDK
публикуется wheel'ом на GitHub. `uv` на этой машине не может проверить TLS-цепочку
`raw.githubusercontent.com` (Let's Encrypt `YR1`, `invalid peer certificate: UnknownIssuer`);
`--native-tls` и `UV_SYSTEM_CERTS=1` проблему не решают, прокси в системе не настроен.

**Решение.**
1. `pyproject.toml` + `uv.lock` — единственный источник истины по зависимостям,
   Python зафиксирован как `>=3.12,<3.13` (SDK не поддерживает 3.14).
2. `requirements.txt` генерируется `uv export` и не правится руками.
3. Wheel SDK 1.51.0 хранится в `vendor/` и подключается через `[tool.uv.sources]`
   с относительным путём — сборка воспроизводима без сети к GitHub.

**Альтернативы.**
- Ставить SDK отдельно через `pip` после `uv sync`: lock неполный, сборка невоспроизводима.
- Оставить прямой HTTPS-URL в `pyproject.toml`: падает на TLS, а также на других машинах
  без доступа к GitHub.
- `pip-tools`: рабочий вариант, но требует отдельного управления интерпретатором.

**Следствия.** `vendor/*.whl` коммитится (316 КБ). При восстановлении официального индекса:
`"t-tech-investments>=1.51"`, удалить `[tool.uv.sources]` и `vendor/`, пересобрать lock.
`tinkoff-investments` (старый SDK, модуль `tinkoff`) и `pandas-ta` в зависимости не
включены — используются только legacy-файлами (T1-3).
