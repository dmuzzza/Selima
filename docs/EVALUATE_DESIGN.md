# Дизайн команды `evaluate <strategy>`

**Статус:** проект, код не написан. Реализация — после T2-22a и T2-23.
**Связанные документы:** ADR-015 (walk-forward), ADR-021 (heatmap), ADR-022 (портфель),
ADR-023 (вердикт), ADR-029 (журнал гипотез).

---

## 1. Задача

Ответить на один вопрос: **эта идея живая или нет** — и ответить так, чтобы ответ нельзя
было улучшить перебором вариантов. Команда собирает входы существующего вердикта
(`src/backtest/verdict.py`) и добавляет то, чего в нём нет:

- учёт числа проверенных гипотез — автоматически, из журнала, а не самоотчётом;
- минимальный детектируемый эффект (MDE) и исход `underpowered`;
- запечатанный OOS-период, который нельзя посмотреть до подтверждения;
- запрет менять параметры внутри одного вызова.

`evaluate` не заменяет `scripts/verdict.py`: вердикт остаётся движком решения, `evaluate`
— обвязкой, которая честно считает, сколько раз этот движок уже спрашивали.

---

## 2. Вход

```bash
uv run python scripts/evaluate.py \
    --strategy dual_ma_crossover_after_testing \
    --hypothesis "Пересечение SMA50/SMA14 после отката: импульс продолжается 2-3 бара" \
    --timeframe 4h \
    --tag my-idea-1
```

| Аргумент | Обязателен | Смысл |
|---|---|---|
| `--strategy <code>` | да | код из `STRATEGY_REGISTRY` |
| `--hypothesis <text>` | да | формулировка идеи **до** прогона; попадает в журнал и отчёт |
| `--timeframe` | нет | по умолчанию из `config/portfolio.json` |
| `--universe` | нет | по умолчанию `config/portfolio.json` |
| `--tickers A,B,C` | нет | ручной набор; считается новой попыткой, список пишется в журнал и отчёт |
| `--grid-cells <N>` | нет | размер сетки, если идея проверялась heatmap; по умолчанию 1. Бюджет не тратит, идёт в screening-поправку и отчёт |
| `--tag` | нет | имя отчёта; по умолчанию `evaluate-<timestamp>` |
| `--unseal` | нет | открыть запечатанный OOS (см. §7); требует пройденного скрининга |

**Запрет.** TP/SL, издержки и состав набора берутся только из конфигов. Команда не
принимает `--tp-percent`, `--sl-percent`, `--spread-bps` и подобных: другая сетка — это
новый прогон, новая строка журнала и новая попытка. Без этого `evaluate` превращается
в оптимизатор.

**Отказ при незаполненном календаре.** Если покрытие дивидендов (T2-22a) или weekend-бары
(T2-23) не готовы для набора, команда печатает предупреждение и **не ставит** `works`:
цифры без календаря — не доказательство.

## 3. Журнал гипотез

### 3.1 Формат

Файл `journal/hypotheses.jsonl`, одна строка — одна запись, только дозапись (append-only).
Правка и удаление строк запрещены: история попыток — часть доказательства.

```json
{
  "recorded_at": "2026-11-07T09:15:00+00:00",
  "kind": "idea",
  "hypothesis": "Пересечение SMA50/SMA14 после отката: импульс продолжается 2-3 бара",
  "strategy": "dual_ma_crossover_after_testing",
  "timeframe": "4h",
  "tickers": ["AFLT", "ALRS", "CHMF"],
  "universe_source": "portfolio",
  "config_sha256": "9f2c...e41a",
  "grid_cells": 20,
  "sealed_access": false,
  "tag": "my-idea-1",
  "notes": "",
  "prev_hash": "0f3a...9c21"
}
```

| Поле | Смысл |
|---|---|
| `kind` | `idea` (новая гипотеза, тратит бюджет) или `sealed` (обращение к запечатанному OOS, бюджет не тратит) |
| `config_sha256` | sha256 канонического JSON параметров прогона (стратегия, TP/SL, издержки, набор) |
| `grid_cells` | сколько ячеек сетки просмотрено в рамках идеи; 1 — без сетки. Не бюджет, а вход screening-поправки |
| `sealed_access` | обращение к запечатанному OOS (см. §7) |
| `universe_source` | `portfolio` (20 фиксированных) или `manual` (`--tickers`) |
| `prev_hash` | SHA-256 канонического JSON предыдущей строки; первая — `GENESIS_HASH` (`0`×64) |

**Хеш-цепочка.** `load_hypotheses()` проверяет цепочку при каждом чтении: правка, удаление
или перестановка строк даёт `broken hash chain` с номером строки. Append-only в git можно
тихо переписать; цепочку — только пересчитав все последующие строки, что видно в diff.
`verify=False` — только для разбора повреждённого файла. Предел: пересоздание журнала
целиком с пересчётом всех `prev_hash` цепочка не ловит; следующий уровень — фиксировать
последний хеш вне журнала (сообщение коммита или отдельный файл).

**Коммит.** Строку журнала коммитит **пользователь** сразу после прогона, в том же
коммите, что и отчёт. `evaluate` в git не пишет: команда, которая сама коммитит, может
захватить лишнее. Незакоммиченный журнал обнуляется откатом ветки или `git checkout` —
поэтому `evaluate` проверяет `git status --porcelain journal/` и предупреждает (§4, шаг 9).

### 3.2 Два счётчика, намеренно разные

- **Идеи** — бюджет: записи `kind="idea"`, глобально по всем стратегиям и вселенным.
  Не по паре «стратегия + идея»: проверяется много разных идей, и поправка должна
  считать именно их.
- **`grid_cells`** — сколько вариантов параметров просмотрено внутри идеи. Идёт в отчёт
  и в screening-поправку, но квартал не сжигает.

Следствия, которые надо принять явно:

- heatmap из 20 ячеек — **одна** идея и 20 `grid_cells`, а не 20 идей;
- новое имя стратегии не обнуляет счётчик;
- ручной `--tickers` — отдельная идея;
- перезапуск на исправленной модели (`model_revision`) **не** новая идея, но в журнале
  остаётся две записи с разными `config_sha256`;
- `kind="sealed"` — не идея: обращение к подтверждению, бюджет не тратит, `k` увеличивает.

### 3.3 Бюджет

`TRIAL_BUDGET_PER_QUARTER = 20` **идей** на календарный квартал (в `config/validation.json`,
секция `evaluate`). `record_attempt()` бросает `TrialBudgetExceeded` **до** записи: прогон,
который превысил бы бюджет, не начинается — сначала нужно закрыть квартал и записать вывод
по гипотезам, а не продолжать перебор.

Альтернатива «бюджет в ячейках» (например, 200 `grid_cells`) отвергнута: она смешивает
две разные вещи — сколько идей проверено и насколько широко каждая из них перебиралась.
Первое ограничивает число независимых вопросов к данным, второе — глубину перебора внутри
вопроса; их учёт разными счётчиками честнее.

Обоснование числа — в §5.1: 20 попыток дают множитель к MDE ≈ 1.54, что оставляет
достижимым edge 20–30 bps на текущей выборке. Меньший лимит (10) даёт 1.43, больший (50) —
1.68 и делает `works` практически недостижимым.

## 4. Конвейер

Нового движка нет, шаги переиспользуют существующее:

1. `prepare_candles()` → `strategy.run()` по каждому тикеру с `CostModel` из
   `config/costs.json`.
2. Пул сделок, блочный bootstrap 30 дней → CI net bps (`portfolio.py`).
3. Дивиденды (`dividends.py`, T2-22) и weekend-бары (T2-23) — пометка и покрытие.
4. ×2 издержек, `tp_penalty`, leave-one-out → `VerdictInputs`.
5. Heatmap вокруг **торгуемой** точки — плато (`heatmap.py`).
6. Null-тест на тех же данных (`null_test.py`).
7. MDE и решение по §5–§6.
8. Запись строки в журнал (до печати отчёта: если прогон упал, попытка всё равно учтена).
9. Проверка коммита журнала: `git status --porcelain journal/` — если после записи
   появились незакоммиченные строки, отчёт печатает предупреждение с их числом
   (`journal: 1 uncommitted row — commit it, an uncommitted journal loses the trial
   counter on checkout`). Git недоступен (запуск вне репозитория) → «git unavailable,
   check the journal manually». Молчать нельзя: незакоммиченный журнал обнуляется
   откатом ветки или `git checkout`. Коммитит пользователь — `evaluate` в git не пишет.

## 5. Исходы: пять состояний вместо четырёх

Порядок жёсткий, первая сработавшая группа решает:

| Порядок | Состояние | Условие |
|---|---|---|
| 1 | `rejected` | верхняя граница CI95 пула **или** подтверждающего периода ниже `target_edge_bps` |
| 2 | `underpowered` | `MDE_adj > target_edge_bps` и CI не исключает целевой edge |
| 3 | `inconclusive` | мощности хватает, но CI содержит ноль и не исключает edge |
| 4 | `fragile` | положительный, но не выжил ×2 издержек / LOO / плато / подтверждения |
| 5 | `works` | положительный на скрининге, подтверждён на запечатанном OOS, выжил все проверки |

`target_edge_bps = 10.0` — минимальный эффект, который стоит торговать после издержек
(в конфиге, до прогона). `rejected` означает «доказано, что эффект **меньше нужного**»,
а не «ноль не исключён».

### 5.1 MDE

Минимальный детектируемый эффект:

```
SE     = (CI_high - CI_low) / (2 * z_0.975)      # z_0.975 = 1.96
MDE    = z_(1 - alpha_adj / 2) * SE
MDE_adj = MDE с поправкой на n_trials
```

Порядок величин на текущих данных (σ ≈ 295 bps, выведена из CI на 929 сделках
`[−15.53; +22.42]`):

| Сделок | Без поправки | 10 попыток | 20 попыток |
|---|---|---|---|
| 929 | ≈ 19 bps | ≈ 27 bps | ≈ 29 bps |
| 1711 | ≈ 14 bps | ≈ 20 bps | ≈ 22 bps |
| 3345 | ≈ 10 bps | ≈ 14 bps | ≈ 16 bps |

Числа — оценка по σ, точное значение печатает отчёт. Оценка «25–30 bps при 10 попытках»
соответствует выборке 929 сделок (строка 1 таблицы): на ней поправка действительно
требует почти вдвое более широкого интервала, чем текущий. При 1711 сделках и бюджете
20 попыток edge 10 bps **неразличим** — исход `underpowered`, а не `rejected`. Чтобы
видеть 10 bps с поправкой, нужно ≈ 3 300 сделок, то есть либо больше тикеров, либо
меньший таймфрейм.

### 5.2 Что из этого следует для выбора идей

`MDE` падает как `1/√n`, а не как `1/n`: удвоить выборку — значит уменьшить порог всего
в 1.4 раза. Практический вывод: на текущем пуле (≈ 1 700 сделок, 4h, 20 тикеров) идею
с ожидаемым edge 10 bps доказать нельзя за разумное время, и почти каждая такая идея
получит `underpowered`. Это не провал идеи, а нехватка данных — и отчёт обязан говорить
именно так.

Поэтому первые реальные идеи выбираются по одному из двух признаков:

- **больший edge на сделку** — событийные стратегии с редкими, но сильными движениями
  (дивидендные гэпы, пост-дивидендный дрейф): десятки bps на сделку различимы уже
  на 300–600 сделках;
- **большее число сделок** — шире вселенная или меньший таймфрейм: 1h вместо 4h даёт
  в разы больше сделок, но и больше издержек на круг, поэтому выигрыш надо проверять,
  а не предполагать.

Идеи «улучшим существующую MA-стратегию на пару bps» на этой выборке проверять
бессмысленно: они упираются в мощность, а не в качество идеи.

## 6. Множественность: две ступени

### Ступень 1 — скрининг на обучающем периоде

Данные до `holdout_start` (`2025-10-01`). Мягкий критерий: точечная оценка > 0 и
CI80 исключает ноль (или p < 0.2 по bootstrap). Здесь работает `grid_cells`: чем шире
перебор внутри идеи, тем выше порог скрининга. Ступень **ничего не доказывает** и
не печатает `works`: её задача — отсеять заведомо мёртвое и не тратить обращения
к запечатанному периоду.

### Ступень 2 — подтверждение на запечатанном OOS

Одна проверка на гипотезу, уровень `alpha_confirm = 0.05 / k`, где `k` — число
обращений к запечатанному периоду (счётчик `sealed_access` в журнале). Это Holm-подобная
поправка с явным семейством: чем чаще открывали запечатанные данные, тем выше порог.

Почему не Бонферрони по всему пулу сразу: он применяется к интервалу, который и так
строится на 1711 сделках, и при 20 попытках требует edge 22 bps — это отвечает на вопрос
«видим ли мы 10 bps», а не «есть ли edge». Поэтому жёсткая поправка применяется только
на подтверждении, а на скрининге — мягкий критерий.

### Разработочный holdout

`2025-10-01…2026-10-01` просмотрен многократно на `dual_ma` и больше не независим.
Он остаётся в отчёте как **development validation** и не даёт `works`: максимум
`fragile`. Независимым считается только запечатанный период (§7).

## 7. Запечатанный OOS

- Период: **после `2026-10-01`** (граница в `config/validation.json`, секция `evaluate`).
- По умолчанию `evaluate` его не читает и печатает `sealed period: not accessed`.
- `--unseal` разрешён только при пройденной ступени 1; каждое обращение пишет в журнал
  строку с `sealed_access: true` и увеличивает `k`.
- Один прогон `--unseal` — одна проверка на гипотезу. Повторное открытие по той же
  гипотезе с изменёнными параметрами — новая гипотеза и новое `k`.
- Финальный судья — **paper trading вперёд** (`TRADING_MODE=dry_run`, реальные сигналы,
  без ордеров). Бэктест на запечатанном периоде — допуск к paper, не доказательство
  прибыльности.

## 8. Выходной отчёт

Порядок фиксирован:

```markdown
# Evaluate: dual_ma_crossover_after_testing / 4h
Hypothesis: <текст из --hypothesis>
Ideas this quarter: 7 of 20 (this run adds 1, grid_cells 20)

## Verdict: underpowered
Reason: MDE 22 bps > target 10 bps; the sample cannot see the edge we need.

## Numbers
pool (train)      1200 trades   +4.10 bps  CI95 [-12.0; +20.2]
development       228 trades   -15.83 bps  CI95 [-57.26; +32.35]
costs x2          ... ; TP penalty ... ; without best ticker ...
sealed OOS        not accessed

## Power
sigma 295 bps | MDE 14 bps | MDE with 20 trials 22 bps | target 10 bps
trades needed for target: ~3345

## Checks
null ok | plateau no_plateau (5/8) | tradable true | dividend coverage 3/20

## Assumptions
T2-17a: short through an ex-dividend date is assumed to pay the gross dividend.

## What would change the verdict
- pool must reach ~3345 trades for a 10 bps target at 20 trials
- sealed OOS must exclude zero at alpha 0.05/1 after screening
- x2 costs must keep the lower bound above zero

## Biases
The 20-ticker universe was chosen by today's liquidity: survivorship bias.
Manual --tickers runs are recorded separately and count as a new trial.
```

Секция **What would change the verdict** обязательна и должна называть число, а не
направление.

## 9. Ограничения, которые фиксируются в отчёте

1. Набор 20 тикеров выбран ретроспективно по сегодняшней ликвидности — смещение
   выжившего (ADR-022).
2. `n_trials` считается по журналу, но журнал начинается с даты его введения:
   гипотезы, проверенные до неё, известны только по документации (ADR-023, `n_trials`
   в отчётах). Первая запись журнала должна их перечислить.
3. MDE — оценка по σ из текущего пула; при смене таймфрейма её надо пересчитать.
4. `evaluate` не проверяет качество данных: пропуски и неполные бары остаются
   ответственностью загрузчика.

## 10. Порядок работ

| Шаг | Что | Зависимость |
|---|---|---|
| 1 | `src/backtest/hypothesis_log.py` + тесты + `journal/hypotheses.jsonl` | нет |
| 2 | T2-22a: дивиденды на 20 тикеров | нет |
| 3 | T2-23: weekend-бары, доля сделок и гэпы | нет |
| 4 | `evaluate`: конвейер, MDE, исходы, отчёт | 1–3 |
| 5 | `--unseal` и paper trading | 4 |

Шаг 1 не зависит от календаря и делается первым: без журнала поправка на
множественность не работает, а всё остальное её использует.

**Приёмка шага 4:** незакоммиченный журнал определяется проверкой
`git status --porcelain journal/` и печатается в отчёте с числом строк; вне git —
сообщение «git unavailable, check the journal manually». `evaluate` не коммитит: журнал
коммитит пользователь, вместе с отчётом. При появлении `docs/OPERATIONS.md` (T6-7)
правило переезжает туда.
